## 4. Interpretation (separate from the measured numbers above)

- **H1 (token cost): supported, with an important nuance.** By the offline tokenizer proxy — which
  counts only the skill-mechanism tokens each approach introduces (tool schemas + resolve result +
  fetched body for Alexandria; all skill frontmatter + matched body for native) — Alexandria is
  ~11.6× cheaper and the gap grows with library size. **However**, Claude's *reported* total usage
  shows Alexandria slightly higher, because the agentic MCP round-trips (resolve → fetch → reason)
  add conversation turns and cached context that the proxy intentionally excludes. The clean,
  mechanism-level claim (resident skill-definition tokens) favors Alexandria and scales with N; the
  end-to-end token claim is murkier at N=20 and should be revisited at larger N.
- **H2 (latency): native faster, but immaterial.** 1.3 ms (local file read) vs 25 ms (HTTP
  resolve+fetch). Both are trivial next to model generation; not a decisive axis.
- **H3 (accuracy): native wins decisively (83% vs 19%).** With compliance identical (42/42), this is
  not a "who consulted more" artifact — it is retrieval quality. When Alexandria is consulted, its
  full-text resolver surfaces the gold skill in only 20% of cases (recall@5 = 8/40), so the agent
  usually can't choose correctly. Native, with every skill's description resident in context, lets
  the model pick correctly 93% of the time it consults.
- **The core finding is a tradeoff:** Alexandria trades retrieval *accuracy* for context *economy*.
  Its Postgres full-text resolver has poor recall (~20%) on the verbose natural-language queries an
  LLM generates (e.g. "generate Excel workbook from CSV with formulas multi-sheet" matches nothing,
  while "Excel workbook" matches). This points directly at Alexandria's planned Phase 2 semantic
  search (pgvector) as the lever to close the accuracy gap while keeping the token advantage.

## 5. Threats to validity

- **Pilot scale:** N = 20, single rep, one model (`claude-haiku-4-5`) at low effort. No dispersion
  (nrep = 1). Treat magnitudes as indicative, not final.
- **Model strength:** a weaker/cheaper model. A stronger model may write better resolver queries
  (raising Alexandria recall) and/or comply more consistently; untested here.
- **Tokenizer proxy vs reported usage disagree in direction** (see H1). The proxy is a controlled,
  reproducible mechanism-level count; reported usage includes agentic overhead. Both are reported;
  neither alone is the whole story at this scale.
- **Accuracy is apples-to-oranges by construction:** native = LLM choosing from resident
  descriptions; Alexandria = FTS rank → LLM fetch. This is the real product comparison, not a pure
  retrieval-algorithm benchmark.
- **recall@5 is Alexandria-only** (native has no candidate list), so cross-condition accuracy is
  compared via model-choice, not recall.
- **Decision-only regime:** the agent is told to consult-and-stop; this isolates skill *selection*
  from task *execution*. Numbers describe selection behavior, not end-to-end task success.
- **Scope:** single machine, Claude Code only, this 20-skill corpus. No generalization beyond it.

## 6. Reproduce

```bash
cd experiments && source .venv/bin/activate   # Python 3.11+ with requirements.txt
export TOKEN=$(curl -s -X POST http://localhost:9000/alexandria/token \
  -d grant_type=client_credentials -d client_id=alexandria-client -d client_secret=any -d scope=openid \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")
python -m harness.run_experiment --sizes 20 --nrep 1 --warmup 0
# then: python -m harness.aggregate --records results/raw/<run-id>/records.jsonl --out results/computed/<run-id> --k 5
```
