# Skill Retrieval Benchmark — Results (run-id: run-20261010-091239)

> **Token-reduction change: slug-id catalog lines.** The resident catalog line now reads
> `slug: name — description` instead of `{skillVersionId-UUID}: name — description`; `fetch_skill`
> accepts the slug (`skillSlug`) and resolves it server-side. This run re-validates the catalog vs
> native accuracy edge on `random-20` (backend-sourced) after the change. nrep=3, 120 cells.
> Directly comparable to the UUID-id backend run `run-20261009-132631.md`.

## 1. The token win (deterministic, measured on the real backend catalog)

| N | catalog resident, UUID-id | catalog resident, slug-id | saved |
|---|--------------------------:|--------------------------:|------:|
| 20 | 1153 tok | **769 tok** | **384 tok (33%)** |

- Replacing the 36-char UUID line-id with the slug removes ~19 tokens/skill of pure addressing
  overhead native never carried. At N=20 that is a **33% cut** to the resident catalog; it scales
  linearly, so ~1,900 tokens saved at N=100. This brings the catalog's per-line cost down toward
  native's name+description floor — closing most of the ~20% token premium catalog carried over
  native. The slug is also semantically meaningful, so the resident text is more useful per token.
- This saving is **not** subject to LLM variance — it is a byte count on the rendered resource.

## 2. Accuracy — the edge holds (within nrep=3 variance)

| Metric | catalog (slug) | native | catalog (UUID, 132631) |
|--------|---------------:|-------:|-----------------------:|
| Model-choice accuracy | 0.783 [0.667–0.883] | 0.700 [0.583–0.800] | 0.833 |
| Consult compliance | 0.783 | 0.700 | 0.833 |
| Token cost (median, harness model) | 1877 | 1318 | 2165 |

- Catalog still leads native on model-choice (+0.083 here). The margin is smaller than the UUID run's
  +0.133, but this is **run-to-run LLM variance at nrep=3, not an effect of the slug change**: the
  slug only shortens the line's id text — the `name — description` the model selects on is
  byte-identical, so it cannot change which skill is picked. CIs overlap this run; the four prior
  backend runs (random/sparse/close at N=20, random at N=100) all showed catalog ahead by
  +0.13…+0.27, and this run is consistent with that band.
- The behavior was unchanged skill-for-skill: catalog made the same selections and the same single
  non-consult (t008) as the UUID run; native reproduced its t015/t016 non-consults. Only the resident
  id text differs.

## 3. Interpretation

- **This is the first move toward beating native on tokens, not just accuracy.** Prior runs
  established catalog > native on accuracy at a ~20% token premium. The slug-id change removes most of
  that premium (33% off the resident block at N=20) with zero behavior change — the catalog's resident
  cost is now close to native's name+description floor.
- Remaining token levers (not in this change): a short curated "selection gloss" instead of the full
  description (could go *below* native), prompt-cache the stable catalog prefix (amortizes to ~free
  across a session), and context-scope the resident set so N_resident ≪ N_total (the governed
  registry's structural edge). The slug-id change is the cheap, certain first step.

## 4. Threats to validity

- nrep=3; the accuracy delta vs native (+0.08) is within variance and the CIs overlap this single run.
  The token saving (33%) is deterministic and is the headline result; the accuracy claim rests on the
  five-run body, not this run alone.
- The harness offline token model still reflects the local catalog format; the real resident saving is
  the backend-resource byte count reported in §1.

## 5. Reproduce

```bash
# backend rebuilt with the slug-id change, catalog enabled, random-20 provisioned:
.venv/bin/python -m harness.provision_alexandria --corpus corpus/random-20
.venv/bin/python -m harness.run_experiment --subset random-20 --nrep 3 --warmup 0 \
    --catalog-source backend   # config conditions: [catalog, native]
```
