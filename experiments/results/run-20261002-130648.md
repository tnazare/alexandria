## 3. Headline — hierarchical disclosure FAILS on compliance (H3)

| Metric | hierarchical (n=60) | catalog (this run, n=27) | catalog (full baseline) | native (baseline) |
|--------|--------------------:|-------------------------:|------------------------:|------------------:|
| **Consult compliance** | **0.383** | 1.00 | 0.867 | 0.683 |
| **Model-choice accuracy** | **0.183 [0.10–0.28]** | 1.00 | 0.867 | 0.683 |
| Token cost (median) | 145 | 2668 | 2165 | 1657 |
| Retrieval latency (median) | 7.1 ms | 0.43 ms | 0.44 ms | 1.05 ms |

- **The category-open hop collapses compliance: 0.383 vs catalog's 0.867–1.0.** In ~62% of cells the
  agent never engaged the index at all (`opened=0`, token cost 145 = resident headers only). The extra
  required step — pick a category, call `list_category`, *then* decide — gave the model an earlier
  place to disengage, and it took it often.
- **Model-choice 0.183 is far below catalog/native.** Two compounding failures: (a) the compliance
  collapse above, and (b) when it did open a category, it sometimes opened the wrong one or opened one
  then declined to fetch (`consulted=True, chosen=None`) — a navigation miss the flat catalog cannot
  have.
- **The "low token cost" (median 145) is an artifact, not a win.** Hierarchical looks cheap only
  because it usually did nothing. Among cells where it actually opened a category and fetched, cost
  rose to ~1100–2700 — in line with the token model. The sub-linear *resident* cost is real (headers
  are ~145 tokens regardless of N), but it buys nothing if the agent won't navigate.

## 4. Interpretation — the token model was right, the behavior was not

The offline token model (`token-scaling-hierarchical-20261002.md`) correctly predicted hierarchical's
sub-linear **resident** cost (~flat headers, one category disclosed on demand). This live run tests the
part the model could not: **does the agent still consult when selection requires navigating a
hierarchy?** On random-20 at N=20 with haiku/low: **no.** The extra hop is a net loss — it trades the
catalog's single resident decision ("pick a skill id") for a two-step one ("pick a category, then pick
a skill"), and the model abandons the harder path far more often.

This cleanly separates the two levers established earlier:
- **Resident selection drives compliance** (catalog's win). Keep it one step.
- **Fewer resident tokens is cheap only if the agent still engages.** Hierarchical saves tokens by
  adding friction that suppresses engagement — the wrong trade.

**Verdict: hierarchical disclosure as prototyped is not worth pursuing at this scale.** Catalog remains
the mechanism of choice: one resident step, highest compliance, at a modest linear-in-N token premium.

## 5. Threats to validity (and why they don't rescue hierarchical)

- **Lopsided clusters.** `suggest_k(20)=4` produced category sizes [1, 1, 9, 9] on random-20 (a
  deliberately incoherent subset), so some categories are near-useless. This hurts navigation — but it
  cannot explain a 0.38 *consult* rate, since non-consult means the agent never even opened a category
  to discover a bad cluster. The compliance collapse is upstream of cluster quality.
- **random-20 is the weakest subset for a hierarchy** (random libraries don't cluster). A semantically
  coherent library might navigate better — but the point of hierarchical disclosure was to help at
  *large, diverse* N, which random-20 approximates in miniature. A coherent-subset retest could be run
  (`close-semantics-20`), and would be the fair follow-up if revisiting the idea.
- **Model/scale.** haiku/low, N=20, nrep=3. A stronger model might navigate more diligently; the extra
  hop's compliance cost may shrink at larger, more capable models — untested.
- Catalog here is a partial (n=27) but matches its full baseline (compliance 1.0 / accuracy 1.0 on the
  completed tasks), so the comparison is sound despite the quota abort.
