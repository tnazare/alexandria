# Skill Retrieval Benchmark — Results (run-id: run-20261010-071938)

> **Scaling test: backend-sourced catalog vs native at N=100** (`random-100`), nrep=3. The first
> N=100 live run against the real `alexandria://catalog` MCP resource (fetch routed through the
> backend). 100 skills provisioned (100/100 versionIds mapped; catalog 22,411 chars resident). 40
> tasks × 2 conditions × 3 reps = 240 cells, n=120 per metric cell — the largest sample in the suite.
> Tests whether the catalog's N=20 accuracy edge holds or widens at 5× the library size.

## 1. Run metadata

- date `2026-10-10T07:19:38-0400`; model `haiku`, effort `low`; tokenizer `cl100k_base`
- subset `random-100`; **N=100**, nrep=3, warmup=0; conditions **catalog + native**
- `catalog_source=backend`; backend `ALEXANDRIA_CATALOG_ENABLED=true`, `search_mode=hybrid`,
  `maxEntries=500` (all 100 fit, no truncation)
- Integrity: 240/240 cells, 0 poison records

## 2. Headline — the edge widens at scale

| Metric | catalog (N=100) | native | Δ | (catalog N=20 random, for ref) |
|--------|----------------:|-------:|--:|-------------------------------:|
| **Model-choice accuracy** | **0.850 [0.783–0.908]** | 0.683 [0.600–0.767] | **+0.167** | +0.133 |
| Consult compliance | 0.850 | 0.725 | +0.125 | +0.133 |
| Token cost (median) | 5738 | 4668 | +23% | +20% |

- Catalog model-choice **0.850** vs native **0.683** — a **+0.167** edge with non-overlapping CIs at
  n=120. The gap is *larger* than at N=20 (+0.133 on the same random subset), confirming the scaling
  thesis: as the library grows, native's resident-but-often-skipped full preload degrades faster than
  the catalog's compact resident lines. Compliance drove it (0.850 vs 0.725) — native skipped
  consulting on ~27% of N=100 cells (whole-task runs of non-consults observed: t021, t027, t018…).
- Token premium ~23% (5738 vs 4668 median), consistent with N=20. The resident catalog floor is now
  ~4300 tokens (paid even on a non-consult), ~5× the N=20 floor — linear-in-N, as modeled. This is the
  cost side of the tradeoff, unchanged in character at scale.

## 3. Interpretation — four subsets, one verdict (real backend)

| Run | N | catalog | native | Δ |
|-----|--:|--------:|-------:|--:|
| random-20 (`132631`) | 20 | 0.833 | 0.700 | +0.133 |
| sparse-20 (`142645`) | 20 | 0.983 | 0.833 | +0.150 |
| close-20 (`145503`)  | 20 | 0.967 | 0.700 | +0.267 |
| **random-100 (this)** | **100** | **0.850** | **0.683** | **+0.167** |

- **The catalog beats native on model-choice in every run against the real product resource, and the
  N=100 result shows the margin does not shrink with scale — it grows** (random: +0.133 → +0.167 from
  N=20 → N=100). The lever remains compliance: resident, single-step selection gets the agent to
  engage where native's heavier, flatter preload increasingly does not as N rises.
- **The cost is honest and unchanged:** a ~20–23% token premium that grows linearly in N (resident
  floor ~860 tokens/skill-set at N=20 → ~4300 at N=100). The catalog is an accuracy + governance win,
  not an efficiency win. For a large registry, `maxEntries` / `lifecycleScope` scoping (R5/R6) is the
  lever to cap the resident cost — not revisited here (all 100 fit under the 500 cap).

## 4. Threats to validity

- One N=100 subset (random). A sparse/close N=100 would test whether the widening holds on harder
  selection; random is the neutral baseline and already shows the trend.
- haiku/low, nrep=3; CIs quantify variance and are non-overlapping. The harness injects the backend
  resource resident (simulating a client that loads MCP resources); a production client's handling is
  still the real-world dependency.
- Backend `search_mode=hybrid` is irrelevant to the catalog path (no FTS/semantic step in the listing).
